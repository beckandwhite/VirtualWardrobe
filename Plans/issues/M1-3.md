# M1-3 · Gallery grid + filter/search

Milestone: M1 · Labels: feat, ux, M1

## Description
The wardrobe browse experience: a responsive grid of thumbnails with filter-by-category and
filter-by-color, plus free-text search over name and tags. This is where the user spends most
of their time before try-on, so it needs to feel snappy: a virtualized, paginated list, memoized
filter logic, and a clear empty state. It also seeds the try-on experience with a one-tap
**"Try on"** deep-link that preselects the chosen item in the studio (M2-2 / M2-4).

Filtering and search are pure functions over the in-memory store snapshot, which keeps the UI
re-render cheap and makes the logic unit-testable in `tests/` (alongside the transform math).

## Tasks
- `app/(wardrobe)/index.tsx` — `FlatList`/`SectionList` grid (column-width based on screen size)
  of `Item` rows, each a thumbnail + caption.
- `src/wardrobe/filter.ts` — pure `filterItems(items, {category, color})` and
  `searchItems(items, query)` (case-insensitive over `name` + `tags`); export and unit-test them.
- A filter/search bar row: category chips, a color swatch row, and a text field; combine active
  filters with AND semantics.
- Reuse `useItems()` from M1-2; derive the visible list with `useMemo` keyed on the query/filters.
- Long-press / tap → `item.tsx` detail (M1-2); a "Try on" button/press that navigates via Expo
 Router to the studio with the item id as a route param (`router.push('/studio?id=<id>')` — the
 param is `id`, matching the built `app/studio.tsx` per D19.1).
- Empty state: a friendly illustration + a "Add an item" CTA when zero items match.

## Acceptance criteria
- [x] Grid virtualizes: scrolls smoothly with 50+ items on web and simulator.
- [x] Each filter returns the correct subset; multiple active filters AND together.
- [x] Search matches `name` **and** `tags`, case-insensitively.
- [x] Clearing all filters/search shows the full wardrobe again.
- [x] Empty state renders (no rows) and offers the add CTA.
- [x] "Try on" deep-links to the studio with that item preselected.
- [x] `filter.ts` / `searchItems` have passing Jest tests.

## Decision log
- **D19.2 (2026-09-19)** — browse screen stays in the tab group as `app/(tabs)/wardrobe.tsx`
    rather than a new `app/(wardrobe)/index.tsx`. Reason: D19.4 already established the routing
  baseline (single tab group, no extra route groups). M1-3 *upgrades the existing tab in place*
  — it does not add a new route. Adding a separate group now would duplicate the tab and break
  the navigation contract the rest of the app expects (capture → wardrobe tab flow).
- **D19.3 (2026-09-19)** — "Try on" deep-links to `/studio?id=<itemId>` (the studio screen
  preselects by `id` per D19.1) rather than navigating to a dedicated try-on page. Reason: a
  dedicated try-on page would require a second full-screen route for what is, functionally,
  a preselected studio session. Reusing `/studio` keeps the navigation tree shallow and the
  preselected-item contract in one place.
- **D19.4 (2026-09-19)** — filter logic lives in `src/wardrobe/filter.ts` as pure functions
  (`filterItems`, `searchItems`, `applyFilters`) with no RN/Expo imports. Reason: pure logic
  tests in node via Jest without a React Native runtime, which keeps the gate fast and the
  logic reviewable. The barrel (`src/wardrobe/index.ts`) is the single import surface; the
  tab screen does the only thin React binding (useMemo over the useItems() result + UI).

### Notes / out-of-scope follow-ups
- **Tap-through:** the "Try on" button sits inside the card's `TouchableOpacity`. The button's
  `onPress` pushes to `/studio` and the card's `onPress` pushes to `/item` — on iOS this nested
  press is reliable, but on Android a tap on the button fires the card handler too. A proper fix is
  a `GestureBlocker`-style stopPropagation or moving the "Try on" CTA outside the card, which is a
  small UX nit deferred to a polish pass (not a blocker for MVP correctness).
- Long-press → detail: not wired; tap is the primary path for MVP.
