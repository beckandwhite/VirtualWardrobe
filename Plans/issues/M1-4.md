# M1-4 · Bundled store.json catalog + ingester

Milestone: M1 · Labels: feat, M1

## Description
A built-in catalog so users have something to try on day one, with **zero network** — a direct
consequence of "fully local" (ADR-004) and "both user + catalog" (ADR-002). The catalog lives as
bundled assets (`assets/store.json` + images), and a one-time, **idempotent** ingester copies
`StoreItem` entries into the local store on first run. From the UI, catalog items look like regular
items but carry `source: 'catalog'`, and the user can "add" (copy) one into their own wardrobe to
try it on.

Idempotency matters: the ingester runs at boot, so re-launching must never duplicate rows. We key
catalog entries by a stable `id` (and optionally a checksum of the source file) and `INSERT OR
IGNORE`-style upserts.

## Tasks
- Author `assets/store.json` (~15–20 curated items) with the `StoreItem` shape from
  `01-architecture.md §3` (`id`, `source: 'catalog'`, `name`, `category`, `color`, `imagePaths[]`,
  `specs?`), plus the referenced images under `assets/store/`.
- `src/catalog/ingest.ts` — a boot-time routine that reads the manifest and upserts
  `StoreItem` rows via the M0-3 repo; guard with a "catalog v<N>" flag so it runs once per version
  and is safe to re-run.
- `app/catalog.tsx` — a browseable list/grid of catalog items (reuse the M1-3 grid styling), each
  with a "Try on" action and an "Add to wardrobe" action that copies the `StoreItem` into a new
  user `Item` (own `id`, `source: 'user'`).
- Register the ingester in the app's startup path (e.g. a `useEffect` in the root/layout after
  storage is ready), not on every screen mount.

## Acceptance criteria
- [x] Catalog items render **without any network connection** — 18 curated entries in `assets/store.json`, each resolved to a bundled `assets/store/placeholder-*.png` (no URIs, no fetch).
- [x] First run ingests all catalog entries; a catalog item can be "added" into the user's wardrobe — `runCatalogIngest()` at boot via the version-flag gate; "Add" copies a `StoreItem` into a user `Item` (tags `['catalog']`) and bounces to `/wardrobe`.
- [x] Relaunching/re-running the ingester does **not** duplicate rows — two-layer idempotency: (1) `catalog_ingested === CATALOG_VERSION` short-circuits; (2) even past that gate, per-name dedupe via `planIngest`. Proven by `tests/catalog/ingest.test.ts` against a fake repo (crash-safe: rows present but flag stale → 0 re-inserted).
- [x] A catalog item can be "Try on"'d and preselects in the studio like a user item — "Try on" copies to a user `Item` then `router.push('/studio?id=<newid>')`; the studio preselects by id via `r.getItem` (D19.1).
- [x] Adding a catalog item creates a distinct user `Item` — `r.insertItem` returns a fresh DB id; the catalog row and the copied user row are different ids, different `source`.

## Decision log
- **D19.6 (2026-09-20)** — M1-4 *replaces* M0-4's in-code `seedCatalog()`. `onboarding.finish`
   no longer calls it, and `repo.seedCatalog`/`CATALOG` are deleted; ingestion routes through
  `src/catalog/ingest.ts` + `assets/store.json`, still gated by `catalog_ingested` (same flag,
  one catalog mechanism at a time, per the issue's Supersedes clause).
- **Ingestion point = boot, in the root layout.** `app/_layout.tsx` calls `initStore().then(runCatalogIngest)`
   in a single boot-path effect, *not* on per-screen mount. Reason: ingestion must run once for the
  whole app lifetime, and the layout mounts once at startup — the natural single chokepoint.
- **Idempotency is layered, not flag-only.** The version flag (`catalog_ingested === '1'`) gives
   the common fast path (re-launch = no-op). But a crash between insert and flag-write would leave
  rows with a stale flag; `planIngest` dedupes by `name` so a re-run is still safe. Both layers
  are tested.
- **Catalog images = bundled category placeholders, not real product photos.** The manifest stores
   a path *string* for reference, but the UI resolves by `category` to an imported `assets/store/
   placeholder-*.png` (an `ImageSourcePropType` — handle on native, URL on web). Reason: shipping
  real product imagery is out of MVP scope and any network fetch would violate ADR-004 (local).
   The studio already uses the same "sample asset stands in for a garment-image-less entry" pattern
 (`sampleGarment`), so the catalog reuses that resolution shape.
- **`runIngest` is pure-of-IO via `IngestRepo`.** The core takes a narrow structural repo
  (`getSetting`/`setSetting`/`listStoreItems`/`insertStoreItem`) so a fake repo can drive it in
  node without SQLite/Expo — exactly how `autoBox` and `filter` unit-test.

## Notes
Stays local by default (ADR-004). A remote/live catalog is a future enhancement, not MVP.

## Supersedes
M1-4 **replaces the M0-4 in-code catalog seed** (D19.6): `onboarding.ts` currently calls
`r.seedCatalog()`, which upserts a hardcoded `CATALOG` array with empty `imagePaths`, gated by the
`catalog_ingested` flag. When M1-4 lands, remove the in-code seed and route ingestion through
`src/catalog/ingest.ts` + `assets/store.json`, still gated by `catalog_ingested` (same flag, one
 migration at a time, never two catalog mechanisms at once).
