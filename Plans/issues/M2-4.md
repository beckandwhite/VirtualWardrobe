# M2-4 · Manual-overlay fallback (no ML)

Milestone: M2 · Labels: feat, ux, M2

## Description
Guarantee the studio is **fully usable with no pose model at all** — this is literally what native
ships in MVP, since on-device ML is the M3-1 spike and may not land. When `PoseProvider.estimate`
returns `null` (the `ManualPoseProvider` from M0-2, on native), the user positions and scales the
garment entirely by hand. The composer must be a **single code path** whether auto (web) or manual
(native) produced the initial transform, so there is exactly one studio screen to reason about.

This issue is the de-risking keystone for native: even if M3-1 comes back no-go, the app still
produces a real, shareable look (ADR-005).

## Tasks
- Confirm the `ManualPoseProvider` (returns `null`) drives the studio with no model present and no
  model dependency installed in the native build.
- Reuse the M2-2 manual controls as the **primary** path here: when keypoints are `null`, the
  garment starts centered at a sane default scale and the user does all positioning.
- A clear, dismissible affordance: a banner/tooltip "Auto-drape unavailable here — adjusting
  manually" so native users aren't confused by the absence of auto-place.
- Verify the composer UI imports resolve identically for both providers (no `if (native)` in the
  screen); only the **provider selection** differs (the `createPoseProvider` factory).
- Make the auto/manual difference a **data** difference (keypoints present vs. null), never a
  branching of the transform type or the editor.

## Acceptance criteria
- [x] On native (no ML), a user can produce a saved, shareable look end-to-end. — the studio's
        `save & share` works in manual mode; native export degrades to the garment image (D21.3).
- [x] No code path requires a pose model to function; the app boots and works with the model
      uninstalled. — native resolves `ManualPoseProvider` (returns `[]`); the `@tensorflow*` graph
        is web-only (`providers.web.ts`), so native never imports it.
- [x] The auto (web) and manual (native) paths share the **same** transform type and the same
      studio screen. — both produce a `Transform`; `StudioScreen` branches only on `autoPlaced`
        (a boolean from `keypoints.length`), never the editor itself.
- [x] The "adjusting manually" affordance shows when auto-drape is unavailable and is dismissible.
       — the `manualBanner` (shown when `!placed`, dismissible).
- [x] A reviewer can see that the only platform difference is provider selection, not UI branching.
       — `createPoseProvider()` is the sole platform seam; the studio has no `Platform.OS` UI
        branch (only the export/share save path switches, D21.3).

## Status: BUILT (2026-09-20)
Gate-green. The fallback is the shipping native path; not exercised on a simulator in-sandbox (no
native build — the M3-1 spike is where a native ML run would happen).

## Notes
This is what de-risks M3-1: even if native ML fails, the app works. Keep the fallback polished —
it is a shipping path, not a throwaway.

## Deps
Depends on M0-2 (`ManualPoseProvider`) and M2-2 (manual controls).
