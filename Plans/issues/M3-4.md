# M3-4 · [optional] Account + multi-device sync

Milestone: M3 · Labels: feat, M3, debt

## Description
**Separately scoped / optional.** Adds a real account + **optional** cloud sync of the wardrobe and
looks — things the MVP deliberately omits (ADR-004 "fully local", ADR-007 "guest now, account
later", ADR-006 "WatermelonDB only when sync lands"). This issue exists only to make the future
path explicit; it is **not started in MVP** and should not block or be prioritized over shipping.

Because it introduces personal data leaving the device, it also implies a **GDPR-consent flow**,
which the MVP intentionally avoids. Treat this as a future re-scope, not a feature to ship now.

## Status: PARKED — discovery is not authorized yet

Do not implement this issue until product direction explicitly reopens account and sync work.
The next permitted action is a separately scoped privacy/backend architecture spike.

## Tasks
- Choose an auth provider (Auth0 / Clerk / Firebase) — a **separate decision** (its own ADR if it
  changes the plan).
- Migrate the store from `expo-sqlite` to a sync-aware backend (e.g. **WatermelonDB**), per ADR-006;
  keep `src/store/` as the boundary so screens don't change.
- Opt-in sync of wardrobe/looks: bodies may stay local (ADR-004) or opt into cloud; make **local the
  default** and sync an explicit toggle.
- A GDPR-consent / privacy step that **gates any upload** of personal data (body photos, looks).

## Acceptance criteria
- [ ] A user can sign in and see the **same wardrobe on two devices** (sync round-trips).
- [ ] Sync is **opt-in**; the default install remains fully local (ADR-004).
- [ ] A privacy/consent step gates any upload; no personal data leaves the device without it.
- [ ] The `src/store/` boundary means screens/UI don't need rewrites for the migration.

## Notes
Out of MVP by design. Listed only so the path is explicit. Do not start this until the product
direction actually calls for accounts/sync.
