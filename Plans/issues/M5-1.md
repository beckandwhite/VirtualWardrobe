# M5-1 · [autonomous] Create a GitHub Actions build and security workflow

Milestone: M5 · Labels: tooling, qa, M5

## Autonomous-subagent brief (work this alone, no human in the loop)
You are executing this work item fully autonomously. Do not commit or open a PR. Keep the
workflow minimal, deterministic, and compatible with the package scripts already in the repository.
If a GitHub security feature cannot be verified locally, document the exact repository setting or
permission required rather than weakening the workflow.

## Problem
The repository has local quality gates but no checked-in GitHub Actions workflow to run them for
every push and pull request. Dependency and source-security checks are also not part of the review
path, so regressions or newly introduced risks can reach the default branch without a consistent
automated signal.

## Goal
Add a basic CI workflow that validates the JavaScript/TypeScript project and establishes a practical
security baseline without adding unnecessary build infrastructure.

## Tasks
1. Add `.github/workflows/ci.yml` for pushes and pull requests targeting the default branch.
2. Pin the runner to a supported Ubuntu image and use a current supported Node LTS version consistent
   with the project documentation. Enable npm dependency caching through the setup action.
3. Run `npm ci`, then the existing `npm run typecheck`, `npm run lint`, and `npm test` scripts.
4. Add an `npm audit` check with an explicit severity threshold (start at `high`; document any
   intentional exception rather than hiding failures).
5. Add CodeQL analysis for JavaScript/TypeScript with least-privilege workflow permissions.
6. Add dependency review for pull requests, configured to fail on high-severity newly introduced
   vulnerabilities when the GitHub Advanced Security capability is available.
7. Enable and verify GitHub secret scanning and push protection at repository level; record that
   configuration in the issue or repository documentation because it is not implemented by YAML.
8. Add concurrency cancellation for superseded runs and make action versions explicit and maintained.
9. Validate the workflow syntax and run the same local gates from a clean install where the
   environment permits.

## Acceptance criteria
- [ ] A checked-in workflow runs on pushes and pull requests and is visible in the Actions tab.
- [ ] The workflow installs with `npm ci` and passes `npm run typecheck`, `npm run lint`, and
      `npm test` on the default branch.
- [ ] `npm audit --audit-level=high` (or an explicitly documented equivalent) fails the job for
      high or critical dependency vulnerabilities.
- [ ] CodeQL scans the JavaScript/TypeScript source on pushes and pull requests.
- [ ] Pull requests receive dependency-review results, with high-severity additions blocked when
      the repository plan supports the action.
- [ ] Secret scanning and push protection are enabled, or the exact plan/permission blocker is
      recorded as PARTIAL.
- [ ] Workflow permissions are least-privilege and action versions are explicit.
- [ ] The final issue notes the runner, Node version, commands, scan thresholds, and any limitations.

## Risk
- GitHub Advanced Security features may be unavailable for the repository plan or fork PRs. Keep
  CodeQL/dependency-review failures understandable and record availability limitations.
- `npm audit` can fail on transitive vulnerabilities outside the app's direct control. Do not add
  broad ignores; record the advisory, upgrade path, or narrowly scoped accepted risk.
- Expo projects do not require a native iOS/Android build for this baseline. Device builds remain
  outside scope and are covered by the platform setup items.
